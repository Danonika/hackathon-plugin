## 5. Current OPEN critical/high (27)

These are the findings still open at HEAD (the scan was taken at v0.16.98; the one critical is fixed
in v0.16.99, see section 6). Fix one at a time and verify with `ocr scan --path <file>`.

### [critical/bug] cmd/hackathonkit-ctl/proc_windows.go:40-40
Type mismatch in `errors.Is`: `syscall.OpenProcess` returns an error whose dynamic type is `syscall.Errno`, whereas `windows.ERROR_INVALID_PARAMETER` has dynamic type `windows.Errno`. `errors.Is` first compares via interface `==`, which is false for two different named types, and `syscall.Errno.Is` won't map an arbitrary test-windows.Errno either. As a result this branch never matches, so a nonexistent/exited pid (which OpenProcess rejects with ERROR_INVALID_PARAMETER) is reported as alive. That defeats stale pid-file cleanup: `readPID` will treat every recorded pid as running. Compare against the matching error type, e.g. `syscall.Errno(windows.ERROR_INVALID_PARAMETER)` (as `internal/config/lock_proc_windows.go` does), or switch to `windows.OpenProcess` like `processMatchesPath` does.

### [high/bug] cmd/hackathonkit-ctl/main.go:342-342
Session ID collision: the ID is `s-<second-resolution timestamp>-<pid>`. Two `run` invocations in the same process during the same second (e.g. repeated calls to the testable `run()` entry point, or a supervisor invoking `run` in-process) produce identical IDs. Because `Store.UpsertSession` executes `ON CONFLICT(id) DO UPDATE`, the second run silently overwrites/merges into the first session instead of creating a new one, and subsequent events/EndSession are attributed to the wrong record. Use a higher-resolution or randomized suffix.

### [high/bug] cmd/hackathonkit-ctl/tui.go:145-147
The periodic tick unconditionally bumps `m.gen` before dispatching a fresh load. `loadCmd` may legitimately take up to 5s (its own context deadline), but a tick fires every 2s. Because `applyLoaded` discards any response with `msg.gen < m.gen`, when store queries consistently take longer than the 2s tick interval *every* response is superseded and the dashboard never renders any data (or the newly selected session) even though the queries succeeded. Either do not bump `gen` on periodic refreshes (then the equal-gen response is still accepted), or track an in-flight load and skip starting a new one while it is pending.

### [high/bug] internal/config/lock_other.go:87-89
Reclaiming a stale lock by renaming `path` aside opens a window in which `path` does not exist. Any concurrent `acquireLock` can then succeed via `O_EXCL` and create a fresh lock, while the original holder still believes it owns the (now detached) lock. Because `detachAndRemoveLock` subsequently removes the detached inode when `path` exists, the previous holder becomes a phantom owner and two processes can run the protected read-modify-write (`Manager.SetRoutingMode`) concurrently, corrupting the routing state. On non-Unix (e.g. Windows) `os.Rename` also fails when the destination exists, so the restore path can silently orphan the detached inode. Prefer a scheme that never leaves `path` absent (e.g. keep the authoritative lock and use a separate, uniquely-named guard file, or rely on platform locking), or at minimum make the rename/restore identity check robust and document the residual race.

### [high/bug] internal/control/store.go:321-324
`parseTime` deliberately discards the `ok` result of `parseTimeOK`, so a corrupt (non-empty but unparseable) stored timestamp is silently turned into the zero time. For `ended_at` this is worse than for the others: the code still sets a non-nil `*time.Time` pointing at year 1, i.e. it fabricates a valid-looking time instead of an unset one — exactly the outcome `parseTimeOK`'s comment says callers should avoid. Downstream this is not benign: `RecomputeRisk` uses `sess.EndedAt` as the window end, so a corrupt `ended_at` collapses the global-event window to an empty range and computes risk over no data. The same silent zeroing applies to `created_at`/`updated_at` (and to `ts` in `scanEvents`). Use `parseTimeOK` and return a descriptive error (or otherwise surface) for a non-empty unparseable value rather than fabricating a time.

### [high/bug] internal/learning/learning.go:520-523
PID-less stale-lock reclaim has an ambiguous 0==0 comparison. When a lock has no recorded PID, `lockFile` calls `reclaimLock(lockPath, 0)`. Here `lockOwnerPID(detached)` also returns 0 for a peer's freshly O_EXCL-created lock that has not yet written its PID, so the peer's live lock is indistinguishable from the stale one and gets deleted, defeating the claimed TOCTOU fix. (Repro: two processes reclaim the same PID-less stale file; after the first renames it away and a third process creates a fresh lock, the second reclaimer renames and deletes that fresh lock because it reads 0 == stalePID 0, and both then hold the lock concurrently.) Additionally the restore branch below does `os.Rename(detached, lockPath)` after an `os.Lstat` check, which on Unix can clobber a peer lock created between the stat and the rename. For the no-PID case, gate deletion on the detached file still being older than `lockStaleAfter` instead of comparing PIDs.

### [high/bug] internal/openai/client.go:253-253
The `maxAudioBytes` cap is enforced only against the pre-copy `f.Stat()` size, while `io.Copy(part, f)` reads until EOF with no bound. A file that grows between the `Stat` and the copy, or a symlinked/pseudo file that reports size 0, will be fully accumulated in `buf` without ever hitting the guard — an unbounded-memory path on the request side. Enforce the limit on the bytes actually copied.

### [high/bug] internal/routing/fly/router.go:324-328
`categoryAvailable` returns true for any category absent from `categoryCapabilities`, and `Recommend` (line 232) uses it to choose `Route`. MBrain categories come from an arbitrary, user-supplied training dataset (`cmd/fly-train`), so `mbCategoryScores` can return an unmapped category with a high score that wins route selection. Because the `best` loop only iterates `categoryCapabilities[category]`, that category contributes nothing to `MaxScore`/`Recommendations`. `Result.Route` can therefore name a category that maps to no capability while recommendations come from a different category, and callers such as `internal/tools/system.go` surface this bogus route (this is the still-open P2-071). Treat categories without a capability mapping as ineligible for routing.

### [high/bug] internal/tools/deps.go:122-124
argInt rejects any value outside the 32-bit int range, but `int` is 64-bit on the platforms this project builds for. Valid large integers (e.g. Unix-nanosecond timestamps, 64-bit IDs) are silently replaced by the default, causing wrong behavior in handlers. The guard should match the platform `int` width; on 64-bit builds `int(value)` is safe far beyond `MaxInt32`.

### [high/bug] internal/tools/evaluation.go:544-547
`filepath.EvalSymlinks(root)` preserves the *relative* form of the input: for a relative root it returns something like `"subdir"` (and `"."` for the cwd), whereas `resolveExistingPath(full)` always returns an **absolute** path (it starts with `filepath.Abs`). The containment comparison below (`resolved != resolvedRoot && !strings.HasPrefix(resolved, resolvedRoot+sep)`) therefore fails for every path and `resolveRepoPath` rejects all repo-relative paths with "path resolves outside the repository root". This is reachable in practice: `--repo-root` is a documented relative usage (`docs/HACKATHON-GUIDE.md` shows `hackathonkit-mcp.exe --repo-root .`), and `config.NewManager(root).Root()` returns the flag verbatim without absolutizing. All eval tools (aggregate/calibrate/rank/freeze_bundle and every persistence write) then break. Absolutize the root before resolving symlinks so both sides of the comparison live in the same namespace.

### [high/bug] plugins/hackathonkit/hooks/codex-hooks.json:11-11
Non-standard hook key. The Codex command-hook schema documented in this repo (docs/OCR-BACKLOG.md, see OCR-129) accepts only `type`, `command`, and `timeout`; `commandWindows` is not a recognised field (same key appears on the tool-use and stop entries, lines 24 and 37). Depending on how strictly Codex validates the manifest, this key is either silently dropped — in which case Windows falls back to the POSIX `command`, whose `$PLUGIN_ROOT` cmd.exe cannot expand, so all three Windows hooks break — or the whole manifest is rejected and every lifecycle hook is disabled. Confirm `commandWindows` against the current Codex plugin hook schema, or move the platform split into `scripts/hooks.js` instead of relying on an unverified key.

### [high/security] plugins/hackathonkit/scripts/hackathonkit-mcp-launcher.sh:10-10
`command -v` does not guarantee an absolute path: for a shell function/builtin it returns the bare name, and for a PATH-resolved command it can return a cwd-relative path. There is no re-check that `RESOLVED` actually contains a slash (or is absolute), so `SELF` can remain slash-less. In that case `dirname` returns `.` and `REPO_ROOT` is computed from the caller's working directory — exactly the cwd-derived-root attack the surrounding comment claims to prevent. Validate that the resolved value is absolute before assigning.

### [high/security] plugins/hackathonkit/scripts/hackathonkit-mcp-launcher.sh:69-69
TOCTOU: the earlier `[ -L ... ]` guard is not atomic with this exec. `[ -f ]` and `[ -x ]` follow symlinks, so another local user can replace the regular file with a symlink after the `-L` check and before the exec, and the exec will follow the attacker-controlled link. The `-L` check should be repeated immediately before exec (e.g. reject when `[ -L ... ]`), or the binary should be opened and executed via a file descriptor so the verified inode is the one executed.

### [high/bug] scripts/codex-config.test.sh:12-15
`need_python` only verifies that a `python3` binary exists, but nearly every assertion in this suite hard-imports `tomllib`, which is Python 3.11+ only. On a host with Python 3.9/3.10 the very first `TOP=$(python3 -c 'import tomllib ...')` fails its import; because the assignment's status is that of the command substitution, `set -e` then aborts the whole run with a raw `ModuleNotFoundError` traceback and no `[fail]` summary — exactly the failure mode the harness was written to avoid. Note the generator itself guards this with a `tomli` fallback (see gen-codex-config.sh), while the test has no fallback. Validate the parser capability in the prerequisite check (and either require `tomllib` or introduce a shared module name used by all the inline snippets).

### [high/bug] scripts/codex-config.test.sh:79-79
Unguarded command substitutions defeat the resilience that `run_generator` was written for. If the generator exits non-zero without producing `$WORK/codexhome/config.toml` (the failure path the wrapper is meant to tolerate), `python3 ... open(sys.argv[1])` raises `FileNotFoundError`, and under `set -e` this plain assignment aborts the suite before the later assertions and the failure summary run. The same pattern applies to the `BUDGETS=$(...)` and `INJ=$(...)` extractions. Wrap these reads like the generator calls (e.g. append `|| true`/provide a default, or run them in an `if`), so a generator regression is reported as a normal failed assertion.

### [high/security] scripts/docker-check.sh:46-47
Only a newly created `.env` is hardened to 0600. When `.env` already exists (the common case on a developer machine), its permissions are never tightened: `env-set.sh` deliberately preserves the original mode bits, so a world-readable `0644` `.env` keeps exposing DB/MinIO credentials for the whole run. Note also that `chmod 600 ... 2>/dev/null || true` silently swallows failures, so the printed "(mode 0600)" message can be wrong. Harden the existing file as well.

### [high/bug] scripts/env-set.sh:104-107
Lock staleness is decided solely by `kill -0 "$holder"`. This is unsafe in both directions:
- If the recorded PID has been recycled by an unrelated process, the lock is considered live forever and every writer aborts after the 10 retries, permanently deadlocking the env file until `$LOCK` is removed by hand. There is no absolute-age bound.
- `kill -0` also fails with EPERM when the holder belongs to another user, and the code then returns 0 ("stale"), so a *live* lock can be reclaimed, allowing two concurrent writers.
Consider combining the PID check with an absolute age bound on the lock directory (writes are quick, so a generous bound such as 10 minutes is safe), and treating an inconclusive/EPERM result as "not stale" rather than stale.

### [high/security] scripts/redact.sh:17-18
Fail-closed path signals success and writes the notice to stdout. When `sed -E` is unavailable the script emits the notice on stdout (where it can be consumed as redacted data by downstream consumers, e.g. `... | sh scripts/redact.sh`) and exits 0, so callers cannot distinguish suppression from successful redaction. Write the diagnostic to stderr and exit non-zero so the failure is detectable.

### [high/bug] scripts/repair.ps1:20-21
Relying on `$LASTEXITCODE` to detect a `& script.ps1` child failure is unreliable while `$ErrorActionPreference = "Continue"`: a child that fails via `Write-Error`/a non-terminating error or simply returns (without calling `exit`) leaves `$LASTEXITCODE` at 0 — and it is reset to 0 immediately before the call — so a failed harness sync or prompt install silently passes; conversely, a leaking native exit code can produce a false failure. Check `$?` as well (and/or wrap the call so a terminating error aborts). This applies both to the `scripts/setup.ps1` invocation and to the `sync-harness.ps1`, `gen-mcp-manifest.ps1`, `install-prompts.ps1`, and `write-install-state.ps1` invocations in `scripts/repair.ps1`.

### [high/security] scripts/setup.sh:45-45
`.env` is only checked with `-f`, which follows symlinks. A dangling `.env` symlink makes `[ ! -f .env ]` true, so `cp .env.example .env` writes through the link and creates/overwrites the file at an arbitrary target path, and the later `chmod 600` also follows the link. Refuse a symlinked `.env` before creating/securing it (note the sibling `env-set.sh` explicitly guards against this).

### [high/bug] scripts/sync-harness.ps1:120-122
TOCTOU gap in the live-lock eviction guard. The owner token is snapshotted immediately *before* the move, and compared to the moved directory *after*. That only detects a replacement happening between the snapshot and the move. If a peer has already evicted this (stale) lock and re-created its own live lock before we reach this snapshot, `$ownerBefore` captures the peer's token, `$ownerAfter` equals it, and the code deletes the peer's still-held live lock. Two processes can then hold the mutex simultaneously and interleave the mirror swap. Capture the pid/owner identity at the moment `$stale` is decided (e.g. alongside the pid read) and compare the moved directory against *that* snapshot before deleting, so a lock recreated after the staleness decision is restored instead of removed.

### [high/bug] scripts/sync-skills.ps1:67-68
The lock-metadata writes swallow every error (`-ErrorAction SilentlyContinue`). If the `owner` write fails, the release check in `finally` (`$owner -eq $lockToken`) can never match, so this run's own lock is leaked until the 60s age eviction and every subsequent run fails to acquire it. If the `pid` write fails, the lock has no `pid`, so eviction falls through to the age check and can steal a *live* holder's lock after 60s. The shell twin (sync-skills.sh:149-153) aborts when it cannot record the pid. Do not swallow these writes: fail the run and remove the directory this attempt just created (or have `finally` treat a missing/unreadable owner file as owned when the `pid` still matches this run).

### [high/bug] scripts/sync-skills.ps1:88-88
`Get-Process -Id $holderPid -ErrorAction SilentlyContinue` returns nothing for *any* failure, including access-denied (EPERM) for a holder owned by another user or a more privileged context — indistinguishable from "process not found". Combined with the 60s age gate below, a concurrent invocation can therefore evict the lock of a holder that is still alive and mid-copy, defeating the mutex and allowing two writers to mutate `$dst`. Distinguish a genuine miss (null result) from other errors (e.g. probe with `-ErrorAction Stop` inside a `try` and inspect the exception) before concluding the holder is gone.

### [high/bug] scripts/sync-skills.sh:41-42
Stale-lock detection via `kill -0` is unreliable and can break mutual exclusion. `kill -0` returns 0 for a *reused* PID of an unrelated process, so a genuinely dead holder can be misjudged as live and the lock is never reclaimed. Conversely, when the holder runs as a different user, `kill -0` fails with EPERM (not ESRCH), which this code treats as "stale" and steals a lock that is still held. Consider distinguishing "no such process" from "permission denied" (e.g. fall back to the pid-less grace-period path or consult `ps`/`/proc`) instead of treating any `kill -0` non-zero result as death.

### [high/bug] scripts/sync-skills.sh:50-52
TOCTOU race in lock reclamation. `lock_is_stale` decides staleness and returns, then this `mv` renames the lock aside unconditionally. Between the check and the rename, another waiter can remove the stale lock and create a *fresh* lock, which this `mv` will then rename aside and `rm -rf`, destroying a lock that a live peer currently owns. The rename-aside alone does not restore the mutual exclusion the comment claims. Re-validate the lock's identity (e.g. re-read the `owner`/`pid` token and only remove if it still matches the stale snapshot) immediately before/after the rename, or reclaim by atomically renaming the lock to a per-run name and confirming it still holds the expected token.

### [high/bug] scripts/uninstall.ps1:65-65

Here, uninstalling where the plugin was never registered (or where `codex plugin remove` returns non-zero as a no-op) sets `$codexFail = 1` and makes the whole uninstaller exit 1. Query `codex plugin list` / `codex plugin marketplace list` first (boundary-anchored match on the exact names) and only call remove when present; treat the marketplace removal as best-effort when `marketplace list` is unavailable.

- `scripts/write-install-state.sh:78` _maintainability_ - `mktemp` is not checked: if it fails (no write permission on `configs`, full disk, etc.) `set -e` aborts the script with no diagnostic, so callers only see a bare non-zero exit. Also note there is no lock, so two concurrent runs (e.g. `repair.sh` invoked in parallel) each publish their own snapshot and the last writer silently wins. Report the mktemp failure explicitly (and consider serializing concurrent writers).
